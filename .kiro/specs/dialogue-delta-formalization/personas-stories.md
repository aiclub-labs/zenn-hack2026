## 0. このドキュメントの位置付け

本 doc は dialogue-delta-formalization のスペック駆動開発における **要件定義 / 設計の上流入力**。Persona × JTBD × ストーリーマップ × デモナラティブをここで固め、これを起点に requirements / design を組み立てる。

**用語**: **JTBD** = Jobs To Be Done。「その人が片付けようとしている用事」。役割や属性ではなく行動の動機を表す。新システムが代替する対象は「役職」ではなく「Job」だという思考フレーム。

**proxy 組織方針**: ハッカソン提出は個人部門 (fallback 確定済)。具体社名は出さず、**「エンタープライズコンサルティング業務における特定セクター × ユニット」** の generic な表現を採用。デモストーリーは「戦略コンサル × 製造業」マスを想定。

## 1. Persona Cards (3 種に集約)

> 各カードは **前半 = 今日の現実 (システム導入前)**、**後半 = 新システムに求める能力 / 導入後の指標** に分離。

### Persona A: 知識管理者 Admin — 仮称「シゲル」

| Field | 内容 |
|-------|------|
| Role | エンタープライズコンサルファームの **ナレッジマネジメント担当 / シニアコンサル兼任** |
| 今日の業務状況 | 月次でナレッジ整備会議、属人化レポートに目を通す程度。harvest の仕組みが無く、暗黙知の輪郭自体を言語化できていない。M365 Copilot は導入済だが「Copilot は答えるが個人の判断知は引き出さない」状態 |
| 今日のペイン | 1) 何を組織として拾うべきかの基準が無い <br> 2) 仮に拾えても、別マスへの横展開はゼロから手作業 <br> 3) ベテラン退職リスクは認識しているが手が打てない |
| JTBD | 「特定マスで AI が拾うべき暗黙知の輪郭を、業務を止めずに定義・更新したい」 |
| 新システムに求める能力 | スキーマ CRUD UI、revision 履歴、is_active トグル、マス間のスキーマ複製 |
| 導入後に追う指標 | スキーマ 5-30 件/マス、revision 頻度、reject 率 ≤ 20% |
| 主要 Story | → §2.A |
| 導入後の想定リスク | スキーマ更新が業務側に通知されず認識ズレ → ヒアリング過剰 → 業務離脱 |

### Persona B: 業務ユーザー — 仮称「ハルカ」

| Field | 内容 |
|-------|------|
| Role | **シニアコンサル / PM / 営業** (戦略コンサル × 製造業マスの想定) |
| 今日の業務状況 | 1 日 5-20 回 AI チャット (Copilot 系) で顧客分析 / 提案ドラフトを補助。応答が generic な時は背景を毎回プロンプトに貼り直すか、諦めて自分で書く。**自分が暗黙知を持っていることを自覚していない**ことが多い |
| 今日のペイン | 1) AI 応答が一般論で「自分の顧客に当てはまらない」 <br> 2) 自分の経験を AI に渡す手段が無く、毎回ゼロから説明 <br> 3) 過去の自分の判断が次の応答に反映されない |
| JTBD | 「自分の業務知を AI に教える手間を最小化しつつ、次回以降の AI 応答を自分の文脈に寄せたい」 |
| 新システムに求める能力 | チャット UI、5W1H modal (skip 可)、redact フラグ、過去 record 引用の可視化 |
| 導入後に追う指標 | 1 日のヒアリング介入 1-3 回、skip 率 ≤ 50%、citation「役立った」FB 率 ≥ 60% |
| 主要 Story | → §2.B |
| 導入後の想定リスク | 1) ヒアリング modal が連続してフロー阻害 → 全 skip → corpus が薄い <br> 2) 機密案件 turn の redact 忘れ → 監査懸念 |

### Persona C: レビュアー — 仮称「タケシ」

| Field | 内容 |
|-------|------|
| Role | **シニアコンサル / マネージャー** (Persona B の上位者 or 同マスのベテラン)。**Persona B 自身が自己レビュアーを兼ねるケースもあり** (詳細は §1 末「persona 重複論点」) |
| 今日の業務状況 | 後輩のドラフト相談を ad-hoc で受ける程度。「個人の経験知を組織資産にして良いか」を判断する場は無く、AI 応答の質も承認されないまま現場に流れる。レビュー queue という概念が存在しない |
| 今日のペイン | 1) 組織として品質ゲートが無く、AI 応答のばらつきを誰も裁いていない <br> 2) 個人間で判断が食い違っていても並べて見たことがなく、矛盾を発見できない <br> 3) ベテランの暗黙知が散逸している自覚はあるが、形式化のコスト試算もできない |
| JTBD | 「自分が責任を持てる範囲で corpus 品質を担保しつつ、レビュー作業を 1 件 2 分以内に収めたい」 |
| 新システムに求める能力 | レビュー UI (5W1H 要素 / 重み breakdown / 関連 dialogue turns / 矛盾フラグ表示)、編集差分の自動記録、24h タイマー可視化、conflict_detected の根拠表示 |
| 導入後に追う指標 | 処理時間中央値 ≤ 2 分、承認/編集/拒否比率、expired 率 ≤ 10%、conflict resolution 率 ≥ 80% |
| 主要 Story | → §2.C |
| 導入後の想定リスク | 1) 重み breakdown の意味不明で全件承認 → corpus 汚染 <br> 2) 24h SLA 超過で expired → 業務側に redo 負担 |

### Persona 重複論点 (team で要合意)

- **Persona B (業務ユーザー) と Persona C (レビュアー) を同一人物が兼ねるケース**を MVP で許容するか？
  - 許容案: 自己生成 record を自己承認 (early-stage は速度優先、マス内に reviewer が 1 人しかいない現実への対応)
  - 厳格案: 必ず別人レビュー (品質優先、ただしマス内に reviewer が 1 人しかいないケースで詰む)
  - **暫定推奨**: MVP 許容、デモも自己承認フロー。Phase 2 で「reviewer ロール分離」をオプション化
- **Persona A (admin) と C (reviewer) の兼任**: あり得るがロールは分ける (UI / 権限が違う)

## 1.5 価値仮説 (現状 → これからの体験 → 結果)

各 persona の「一番効くペイン 2 つ」だけ並べる。詳細ストーリーは §2 を参照。

### Persona A: 知識管理者 シゲル

| 現状 (システム導入前の今日) | これからの体験 | 結果 |
|---|---|---|
| 個人の暗黙知が誰の頭にも閉じている。Copilot は質問に答えるが、個人の判断パターンは何も harvest しない | マス開設時に「拾いたい観点」を 5-10 個 Admin UI に書く。それ以降、業務対話の中で観点に沿った暗黙知が自動で記録されていく | 暗黙知が「拾うべきもの」として運用可視化される<br>**スキーマ 5-30/マス、reject 率 ≤ 20%** |
| 仮に 1 マスで暗黙知共有の仕組みを作っても、別ユニットへの横展開はゼロから手作業 | 新マスの行を Cosmos に 1 件入れるだけ、infra も workflow も触らず Day-1 から稼働 | 2 マス目以降が即日開設<br>**新マス開設 ≤ 1 日** |

### Persona B: 業務ユーザー ハルカ

| 現状 (システム導入前の今日) | これからの体験 | 結果 |
|---|---|---|
| AI 応答が一般論で自分の顧客に当てはまらない。毎回プロンプトに背景を貼り直すのに疲れた | 同じマスで質問すると、過去に自分が話した判断が引用付きで応答に出てくる。「前回△△と話したように」と AI 側から触れてくる | 同じ説明を何度もしなくて済む<br>**引用「役立った」FB 率 ≥ 60%** |
| 自分の経験を AI に教える方法が無い。説明する時間も取れず、何を渡せば役に立つかも分からない | AI が「この応答は弱い」と自己判定した turn だけ modal が立つ。5W1H を 5 turn 上限で軽く聞き、いつでも skip 可 | 業務リズムを崩さず暗黙知が形式化される<br>**1 日 1-3 回 / skip 率 ≤ 50%** |

### Persona C: レビュアー タケシ

| 現状 (システム導入前の今日) | これからの体験 | 結果 |
|---|---|---|
| 個人の経験知を「組織資産にして良いか」を判断する場が無く、AI 応答の質も誰も承認しないまま使われている | 候補 record を開くと、5W1H・重み根拠・関連 dialogue turn が 1 画面で見える。2 分以内に承認/編集/拒否を選べる | 組織資産化に品質ゲートが入る<br>**処理時間中央値 ≤ 2 分** |
| 同じ観点について A さんと B さんの判断が違っても並べて見たことがない。AI 応答が場面で揺れても原因が追えない | 既存知識と矛盾する候補は「矛盾あり」フラグでキューに上がり、並べて比較表示される | 矛盾を入口で人間が裁ける<br>**conflict resolution 率 ≥ 80%** |

## 2. 主要 User Stories (persona ごと)

各 story は **Given / When / Then** + 関連 Requirement で記述。

### 2.A Admin (シゲル) のストーリー

#### A1: マス開設時のスキーマ初期定義

- **Given** 新しいセクター × ユニット (例: 戦略コンサル × 製造業) を POC マスとして開設する
- **When** Admin UI で schema field を 5-10 件登録する (field_name / description / expected_value_type / example / ai_baseline_assumption)
- **Then** Cosmos `schemas` collection にマス partition で upsert され、Delta Detector が次の turn から照合対象に含める
- **関連 Req**: 1.1, 1.3, 9.3

#### A2: スキーマの段階的調整

- **Given** 業務ユーザーから「この schema 過剰検知」のフィードバック
- **When** Admin が `is_active = false` でフィールドを無効化
- **Then** 次 turn から検知対象外、revision_id 増分、過去 revision は監査ログ保持
- **関連 Req**: 1.2, 1.4

#### A3: マス追加 (横展開)

- **Given** POC が成功して 2 マス目 (別ユニット) に展開
- **When** Admin が新マスの schema を Cosmos に投入するだけで運用開始
- **Then** infra 変更ゼロ、partition key で自動分離、単一 Foundry workflow が両マスを処理
- **関連 Req**: 9.3, 9.4

### 2.B 業務ユーザー (ハルカ) のストーリー

#### B1: 通常対話 (gap なし)

- **Given** マスに割当てられた業務ユーザーとして AI チャットを開く
- **When** 顧客分析の質問を入力
- **Then** AI 応答が返り、Delta Detector が裏で照合、gap 無しなら通常 turn として記録のみ
- **関連 Req**: 2.1, 2.2, 3.5

#### B2: 暗黙知ヒアリング介入

- **Given** AI 応答の self_critic_score < 5、user 入力との意味的距離が閾値超え
- **When** Hearout Agent が modal で 5W1H 質問を提示
- **Then** ユーザーは回答 (or skip)、ChatExtract follow-up で確認、5 ターン以内で `hearout_records` に保存
- **関連 Req**: 3.3, 4.1-4.6
- **UX 要件**: modal は通常チャットを覆い、文脈見せながら回答できる UI

#### B3: 過去暗黙知の自然な参照

- **Given** 以前のヒアリングで自分が形式化した record が corpus にある
- **When** 同マス内で関連質問を投げる
- **Then** AI 応答に retrieve された record の引用 ID が明示、「○○の判断は前回△△と話した」が見える
- **関連 Req**: 8.1, 8.2, 8.5

#### B4: 機密案件の redact

- **Given** 守秘度の高い顧客名 / 案件コードを含む turn
- **When** redact フラグを ON で送信
- **Then** content は Cosmos に保存されずメタデータのみ、Delta Detector も照合対象外
- **関連 Req**: 2.4, 11.3

#### B5: 矛盾検知時のユーザー通知

- **Given** 同 schema field に対し過去複数 record が異なる見解
- **When** 業務ユーザーが質問
- **Then** AI 応答に「他に N 件の異なる見解あり」と明示、ユーザーが追加情報源を確認可能
- **関連 Req**: 8.4

### 2.C レビュアー (タケシ) のストーリー

#### C1: 通常レビュー (承認)

- **Given** レビューキューに重み 0.7 以上の record が入る
- **When** レビュー UI で 5W1H 要素 + 重み breakdown + 関連 dialogue turns を確認
- **Then** 承認ボタンで `approved` → 自動で Truth Judgment 起動 → 整合性スコア ≥ 0.4 なら corpus.upsert
- **関連 Req**: 6.1-6.3, 7.1-7.3

#### C2: 編集レビュー

- **Given** record の表現が不正確だが内容は有用
- **When** 編集 UI で内容を修正 → 「保存して承認」
- **Then** `edit_diff` が監査ログに記録、reviewer_id / edited_at 付き
- **関連 Req**: 6.4

#### C3: 拒否レビュー

- **Given** record が誤情報 / 個人的見解
- **When** 拒否を選択
- **Then** record `rejected`、該当 schema field は同一ユーザーに対し 7 日 cooldown (再ヒアリング防止)
- **関連 Req**: 6.5

#### C4: 矛盾検知時の人間判断

- **Given** Truth Judgment が atomic claim 整合性スコア < 0.4 を返す
- **When** `conflict_detected` フラグ付きで再提示
- **Then** レビュアーは既存 corpus record (矛盾相手) を比較表示で確認し、どちらを残すか / 両方残すか判断
- **関連 Req**: 7.3

#### C5: SLA expired 通知

- **Given** record がレビューキューで 24h 放置
- **When** 期限超過
- **Then** record `expired`、Discord 通知でレビュアーに alert、業務ユーザー側に redo 必要を通知
- **関連 Req**: 6.6

## 3. User Story Map (タイムライン × persona)

```
時間軸 →     開始              対話運用               レビュー                次回対話
─────────────────────────────────────────────────────────────────────────────────
Admin    [A1 schema 初期定義] [A2 スキーマ調整]   ─                       [A3 マス追加]
                ↓
業務U    ─                  [B1 通常対話]
                            [B2 5W1H ヒアリング] →                       [B3 過去 record 参照]
                            [B4 redact]                                  [B5 矛盾通知]
                                                ↓
レビュアー ─                ─                   [C1 承認]
                                                [C2 編集]
                                                [C3 拒否]
                                                [C4 矛盾判断]
                                                [C5 SLA expired]
─────────────────────────────────────────────────────────────────────────────────
agent側  Schema Manager → Delta Detector → Hearout → Formalization → Truth Judgment → AI Search
```

**critical path** (デモで魅せる線):
A1 → B1 → B2 → C1 → B3 (= 「マスを開く → 対話する → 暗黙知を引き出す → レビュー承認する → 次回参照される」)

## 4. 内部ロール (persona ではないが実装側で扱う)

要件定義で仕様文の主語として登場するが、エンドユーザー persona ではない。要件起こしの際の参考。

| 内部ロール | 役割 | persona との関係 |
|-----------|------|-----------------|
| system | エージェント / Cosmos / 周辺サービス全般 | 仕様文の主語、実装側 |
| operator | ハッカソン期間中の運用者 = オペレータ自身 | デモ後は Admin (Persona A) に吸収可能 |
| architect | spec/design 段階の開発者 = オペレータ自身 | 実装後は登場しない |
| 組織管理者 | テナント / 権限統制を担う管理者 | Admin (Persona A) に統合可能 |

## 5. デモナラティブ (3 分審査用)

審査員に見せる起承転結:

| 段 | 時間 | persona | 画面 | メッセージ |
|----|------|--------|------|----------|
| 起 | 0:00-0:30 | Admin | Admin UI | 「業界 × 領域マスごとに『拾いたい暗黙知』を schema 定義」 |
| 承 | 0:30-1:30 | 業務U | Chat UI + 5W1H modal | 「対話中に AI 出力の不確実箇所を agent が検知、業務 flow を切らない最小介入で 5W1H ヒアリング」 |
| 転 | 1:30-2:15 | レビュアー | Review UI | 「重み breakdown + 矛盾検知付きの HITL レビューで corpus 品質をゲート」 |
| 結 | 2:15-3:00 | 業務U (再) | Chat UI | 「次の対話で過去 record が引用付きで自然に出る = 暗黙知が次に活きた瞬間」 |

**差別化メッセージ**: 「文書から抽出するのではなく、**対話の最中に暗黙知が発生した瞬間を捕まえる**」「Copilot は答えるが暗黙知は harvest しない、我々は harvest する」
